# Customization

Jobsite Twin is a template for a construction general contractor's portfolio + jobsite digital twin, but the patterns generalize to any project-based semantic model. This guide covers adapting it to different customer data.

## 1. Point at a different semantic model

Connections are declared in `fabric.yaml` and generated into `src/fabric.generated.ts`. Add a connection and regenerate:

```bash
npx fabric-app-data add <alias> --from-url "<Power BI or Fabric URL>"
npx fabric-app-data generate -o src/fabric.generated.ts
```

Factories reference the connection by its alias (e.g. `const connection = "model"`). Update the alias in the query factories if you change it.

## 2. Adapt the queries to a new schema

The app expects these logical entities (names are illustrative — remap in the `.dax` files and `columnMetadata` to match your model):

| Concept | Used for |
|---|---|
| projects | portfolio rows, KPIs, risk scatter, project header |
| tasks | per-project task grid, status roll-ups, delay days |
| locations (zones) | 3D floor slabs, per-zone status counts |
| costs | cost / overrun measures |

Relationships the app relies on: `tasks[project_id] → projects`, `tasks[location_id] → locations`, `costs[task_id] → tasks`.

For each visual: run the DAX with `npx fabric-app-data query <alias> --query '<DAX>'`, copy the **exact** output column names into `columnMetadata` keys, then wire the factory. Never guess column names — the CLI output is identical to runtime.

## 3. Zone naming conventions

Zones are rendered as a stacked building by `computeZoneStackOrder`, which parses each `zone_name`:

- `Basement` → placed at the bottom.
- `Floor 1`, `Floor 2`, … → ordered numerically.
- Any other name (e.g. `Mechanical Room`, `Exterior`, `Roof`) is treated as "unknown" and sorted alphabetically **above** the known floors.

To give a new zone name specific vertical semantics (e.g. `Roof` on top, `Exterior` at ground level), extend the parser in `floor-stack.ts` and add a spec case.

### Precondition: `zone_name` must be unique per project

The tasks grid drives 3D selection by resolving a clicked row's **zone name** back to a location id (`locationIdByZoneName`). This requires that within any single project, no two locations share the same `zone_name`. If your data can have duplicate zone names per project, switch the selection driver to a stable id: add the id as a **rendered** `DataGrid` column (the grid only emits select predicates for rendered columns) and key selection off it instead of `ZoneName`.

You can verify uniqueness with:

```dax
EVALUATE
ROW(
    "dup_pairs",
    COUNTROWS(
        FILTER(
            SUMMARIZE(locations, locations[project_id], locations[zone_name], "cnt", COUNTROWS(locations)),
            [cnt] > 1
        )
    ) + 0
)
```

`dup_pairs = 0` (or blank) means zone names are unique per project.

## 4. Theming

Colors and spacing are Tailwind v4 `@theme` design tokens in `src/global.css`. Status colors (Delayed / At Risk / On Track / Complete) live in `task-status.ts` and are shared by the 3D slabs, pills, and charts — change them in one place.

## 5. Synthetic data — task→zone placement (notebook)

The demo data is generated by `notebooks/01_synthetic_data_construction.ipynb`
(repo root), which writes the `dbo.projects / tasks / costs / locations` Delta
tables the semantic model reads. It is deterministic (SEED=42) and idempotent —
re-running replaces the tables with identical data.

Task placement in the 3D twin is driven by a **`TASK_ZONE_AFFINITY`** dict near the
top of the notebook: each task type maps to the zones where that work realistically
happens (e.g. `Excavation → [Basement]`, `Roofing → [Roof]`, `Landscaping →
[Exterior]`). At generation time each task is placed in one of its affinity zones
that actually exists in the project, chosen deterministically via a seeded
`xxhash64` window pick — reproducible, yet spread across floors for visual variety.

To adapt it to your own construction ontology:

- **Edit `TASK_ZONE_AFFINITY`** — add/rename task types and list the zones each
  belongs to. Keep zone names in sync with `ZONE_NAMES`.
- **`ZONE_HEIGHT` + nearest-by-height fallback** — when a project contains none of
  a task's affinity zones (e.g. `Roofing` on a project with no `Roof` zone), the
  task falls to the reachable zone whose height is closest to its target, so
  `Roofing → Floor 3` and `Landscaping → Basement` rather than a random floor.
  Update `ZONE_HEIGHT` if you introduce zones at new vertical levels.
- **Zone-name uniqueness precondition** (§3 above) still applies — the app resolves
  a clicked task row's zone name back to a location id, so `zone_name` must be
  unique per project.
- The three validation cells at the end of the notebook (Section 9) assert every
  placement respects affinity (or the fallback exemption), every Delayed project
  has consistent Delayed tasks, and the row counts hold.
