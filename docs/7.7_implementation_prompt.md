# Task 7.7 Implementation Prompt

Use this prompt with a coding agent to implement Task 7.7.

```text
Please implement Task 7.7 in this repository: https://github.com/ChrisChalmers2/rayfin_hackathon

Start by reading these two files:

- docs/7.7_specification.md
- docs/7.7_test_plan.md

Treat docs/7.7_specification.md as the source of truth for scope, acceptance criteria, and the expected file-change set. Treat docs/7.7_test_plan.md as the source of truth for required automated tests, deployment validation, and manual verification.

Requirements:

1. Implement only Task 7.7.
2. Stay within the file-change set listed in docs/7.7_specification.md unless repo discovery proves another file is the actual integration point. If you touch any extra file, explain why in the PR description.
3. Do not implement Teams notifications, webhooks, Rayfin functions, threaded replies, reactions, display names, or Lakehouse-backed comment writes.
4. Do not commit secrets, `.env*`, deployment-local files, tenant IDs, or Rayfin deployment files.
5. Use the existing Rayfin DAB `Comment` entity and typed Rayfin client path. Do not use raw `fetch`, hand-written GraphQL, direct SQL, or Lakehouse writes for comments.
6. Preserve the existing Fabric semantic-model read path and existing project-detail behavior, including zone selection from the tasks table.
7. Keep the implementation token/context efficient: prefer small focused components, hooks, and tests that map directly to the spec and test plan.

Implementation goals:

- Add project-level comments to the single-project detail page.
- Add task-level comments via a tasks-grid comment-count column and task comments drawer.
- Add a typed comments client layer.
- Add hook/state handling for loading, posting, optimistic append, rollback, and refetch.
- Enforce form validation: empty/whitespace blocked, 2000 chars allowed, 2001 chars rejected.
- Render comment text safely as text, not raw HTML.
- Resolve or document the Rayfin `Comment` primary-key behavior.
- Add honest-vs-spoofed Rayfin identity validation as specified.

Testing:

- Add/modify tests to satisfy docs/7.7_test_plan.md.
- Run from apps/Jobsite_Twin:
  - npm test
  - npm run build

Before finishing, verify every acceptance criterion in docs/7.7_specification.md and summarize:

- files changed,
- tests added,
- test/build results,
- how Rayfin honest-vs-spoofed validation is performed,
- any deviations from the expected file-change set and why.

Open a pull request when complete with a concise summary and verification checklist.
```

## Newbie instructions: branch, build, verify, and PR

Use these steps if you are doing the work manually or supervising a coding agent locally.

### 1. Clone the repo

```bash
git clone https://github.com/ChrisChalmers2/rayfin_hackathon.git
cd rayfin_hackathon
```

### 2. Make sure `main` is current

```bash
git checkout main
git pull origin main
```

### 3. Create a feature branch

Use a short descriptive branch name:

```bash
git checkout -b task-7-7-comments-ui
```

### 4. Read the task docs first

```bash
cat docs/7.7_specification.md
cat docs/7.7_test_plan.md
```

Do not start coding until you understand the required scope and the expected file-change set.

### 5. Install app dependencies

```bash
cd apps/Jobsite_Twin
npm install
```

### 6. Implement the changes

Work from the repository root or `apps/Jobsite_Twin`, but keep edits focused on the files identified in `docs/7.7_specification.md`.

Avoid committing:

- `.env`, `.env.local`, or any `.env*` file,
- `rayfin/.deployments.json`,
- secrets,
- tenant IDs,
- deployment-local config,
- unrelated formatting churn.

### 7. Run automated tests

From `apps/Jobsite_Twin`:

```bash
npm test
```

Fix failures before continuing.

### 8. Run the production build

From `apps/Jobsite_Twin`:

```bash
npm run build
```

Fix build errors before continuing.

### 9. Run or document Rayfin identity validation

Follow `docs/7.7_test_plan.md` for honest-vs-spoofed validation.

At minimum, verify:

1. An honest insert where `user_upn` equals the caller's Rayfin/Entra email claim succeeds.
2. A spoofed insert where `user_upn` is another email fails.
3. No secrets are printed or committed.

If validation requires a Fabric/Rayfin environment that is not available locally, commit a script or instructions that explain exactly how to run the validation without secrets.

### 10. Check what changed

From the repository root:

```bash
git status
git diff --stat
git diff
```

Confirm the changed files match the file-change set in `docs/7.7_specification.md`. If any extra file changed, make sure there is a clear reason.

### 11. Commit the work

```bash
git add <changed-files>
git commit -m "Implement Task 7.7 comments UI"
```

Use a more specific commit message if the work is split into multiple commits.

### 12. Push the feature branch

```bash
git push -u origin task-7-7-comments-ui
```

### 13. Open a pull request into `main`

Using GitHub CLI:

```bash
gh pr create \
  --base main \
  --head task-7-7-comments-ui \
  --title "Implement Task 7.7 comments UI" \
  --body "Implements Task 7.7 per docs/7.7_specification.md and verifies it per docs/7.7_test_plan.md."
```

Or open GitHub in a browser, go to the repository, and click **Compare & pull request** for the pushed branch.

### 14. PR checklist

In the PR description, include:

```markdown
## Summary
- Added project-level comments.
- Added task-level comments drawer and task comment counts.
- Added typed comments client/hook layer.
- Added tests from docs/7.7_test_plan.md.

## Verification
- [ ] `cd apps/Jobsite_Twin && npm test`
- [ ] `cd apps/Jobsite_Twin && npm run build`
- [ ] Honest Rayfin insert succeeds
- [ ] Spoofed Rayfin insert fails
- [ ] No secrets or deployment-local files committed

## Notes
- Primary-key behavior: <fixed or documented>
- Deviations from expected file-change set: <none or explain>
```

### 15. Merge into `main`

After CI passes and reviewers approve:

1. Use the GitHub PR page to merge into `main`.
2. Prefer the repository's normal merge style.
3. Delete the feature branch after merge if GitHub offers the option.
4. Pull the updated `main` locally:

```bash
git checkout main
git pull origin main
```
