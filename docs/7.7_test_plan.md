# Task 7.7 Test Plan — Comments with Entra ID

This file contains the detailed verification plan for [`7.7_specification.md`](7.7_specification.md). It is split out so implementers can keep the main specification compact and load only the test details when needed.

```bash
cd apps/Jobsite_Twin
npm install

npm run build
```

## Unit and component test matrix

### Comment client layer

Files:

- `apps/Jobsite_Twin/src/lib/comments-client.spec.ts`

Required cases:

1. **Project comment scoping**
   - Given comments for Project A and Project B, listing project comments for Project A returns only rows with `project_id = Project A` and no `task_id`.

2. **Task comment scoping**
   - Given comments for Task A and Task B in the same project, listing task comments for Task A returns only rows with Task A's `task_id`.

3. **Project-vs-task isolation**
   - Given one project-level row and one task-level row for the same project, project-level listing excludes the task-level row.

4. **Newest-first sorting**
   - Returned display rows are sorted by `created_datetime` descending.

5. **Create payload shape**
   - Creating a project-level comment omits or nulls `task_id` consistently.
   - Creating a task-level comment includes `task_id`.
   - `user_upn`, `project_id`, `comment_text`, and `created_datetime` are sent through the typed Rayfin client.

6. **Error propagation**
   - Rayfin client failures surface as caller-visible errors and do not get swallowed.

### `useComments` hook

Files:

- `apps/Jobsite_Twin/src/hooks/use-comments.spec.tsx`

Required cases:

1. Loads project-level comments on mount.
2. Loads task-level comments when `task_id` is supplied.
3. Exposes loading state before data resolves.
4. Exposes error state when loading fails.
5. Refetches after a successful post.
6. Shows an optimistic comment immediately after submit.
7. Keeps the optimistic comment after successful create/refetch.
8. Rolls back the optimistic comment when create fails.
9. Does not submit when text is invalid.

### Comment form

Files:

- `apps/Jobsite_Twin/src/components/project-detail/comment-form.spec.tsx`

Required cases:

1. Whitespace-only input disables Post.
2. Empty input disables Post.
3. Exactly 2000 characters enables Post.
4. 2001 characters disables Post and shows over-limit state.
5. Character counter updates as the user types.
6. Post is disabled while submitting.
7. Successful submit clears the textarea.
8. Failed submit keeps or restores the user-entered text and shows an error path.

### Comment thread

Files:

- `apps/Jobsite_Twin/src/components/project-detail/comment-thread.spec.tsx`

Required cases:

1. Empty state displays `No comments yet. Start the conversation.`

## Deployment/Rayfin identity validation

This validation proves the backend RLS policy, which cannot be fully proven by local mocked unit tests.

Suggested file:

- `apps/Jobsite_Twin/scripts/validate-task-7-7-identity.mjs`

The validation may be scripted or documented as exact manual steps, but it must not commit secrets.

### Preconditions

1. The Fabric capacity/workload is running.
2. The app has been deployed with Rayfin data enabled.
3. The tester is authenticated as a real Entra ID user.
4. The tester knows their expected `claims.email` value.

### Required checks

1. **Honest create succeeds**
   - Insert a comment where `user_upn` equals the caller's `claims.email`.
   - Expected: create succeeds and the row can be read back.

2. **Spoofed create fails**
   - Insert a comment where `user_upn` is a different email address.
   - Expected: create is rejected by Rayfin/DAB policy.

3. **Cross-user update/delete fails when available**
   - If a row authored by a second user exists, try to update or delete it as the current user.
   - Expected: update/delete is rejected.

4. **Own-row update/delete policy is consistent**
   - If update/delete helper coverage is included, verify own-row update/delete either succeeds through the typed client or remains server-allowed but UI-deferred.
   - Expected: behavior matches the spec and does not allow impersonation.

### Evidence to capture

Commit one of the following without secrets:

- the validation script with comments describing required env vars,
- a short markdown note containing the exact commands and redacted outputs,
- or test output instructions in the PR description.

Evidence must show:

- honest insert succeeded,
- spoofed insert failed,
- no secret values were printed or committed.

## Manual UI verification

Run inside the Fabric portal embed flow after local build/deploy as appropriate.

1. Open a project detail page.
2. Confirm the project comments panel loads below or near the tasks area.
3. Confirm empty state appears when no project-level comments exist.
4. Post a valid project-level comment.
5. Confirm it appears immediately and remains after refresh/refetch.
6. Confirm author displays as the user's UPN/email.
7. Confirm comment text with HTML-like characters displays as text.
8. Confirm the tasks grid has a comment-count column.
9. Click a task's comment-count cell.
10. Confirm the task comments drawer opens for that task.
11. Post a task-level comment.
12. Confirm only that task's count changes.
13. Close the drawer.
14. Confirm project context and existing zone-selection behavior still work.

## Completion gate

Task 7.7 is not complete unless all required automated tests pass, the build passes, and the Rayfin honest-vs-spoofed validation has evidence.
